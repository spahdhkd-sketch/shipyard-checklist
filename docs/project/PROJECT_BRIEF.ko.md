# GS Safety Checklist — 프로젝트 개요

최종 통합: `2026-08-27` (Asia/Seoul)

## 제품 목적

GS Safety Checklist는 조선소 작업을 위한 한국어 현장 안전 PWA입니다. 작업자는 모바일 기기에서 작업 전 점검을 수행할 수 있고, 직장과 관리자는 기준 정보, 작업지시, 안전 기록, 알림, 보존 및 보고를 함께 파악하고 운영할 수 있습니다.

이 제품의 목표는 현장 작업을 빠르고 이해하기 쉽게 유지하면서, 그 과정에서 생성되는 안전 활동을 감사 가능한 형태로 남기는 것입니다. 불안정한 네트워크 연결, 백그라운드 동기화, 애플리케이션 업그레이드, 동시 편집, 파괴적인 관리 작업은 데이터 안전 경계로 취급합니다.

## 주요 사용자 및 업무 흐름

- **작업자:** 로그인하고, 배정된 작업을 확인하며, 작업 전 안전 점검을 완료하고, 불안전 상태나 자재 누락을 신고하며, 안전 서약에 서명합니다.
- **직장 및 관리자:** 선박, 작업자, 작업 유형, 공구, 점검표 내용, 픽토그램, 작업지시, 보고서, 알림, 안전 설정, 보존 정책 및 운영 통계를 관리합니다.
- **현장 환경:** 한국어 UI, 모바일 우선 상호작용, 간헐적인 네트워크 연결, 설치형 PWA 클라이언트 및 신속한 작업 완료를 최우선 제약 조건으로 둡니다.

핵심 애플리케이션 경로:

| 화면 | 기본 셸 | 용도 |
|---|---|---|
| 홈 | `index.html` | 일일 안전 운영 및 주요 기능 진입점 |
| 작업 전 점검 | `check.html` | 작업 선택, 점검표, 서명 및 제출 흐름 |
| 선박 | `ships.html` | 선박/공정 현황판 및 선박 단위 운영 |
| 이력 | `history.html` | 점검 검색 및 읽기 전용 기록 상세 |
| 빠른 메뉴 / 작업 유형 | `items.html` | 권한별 경로 및 작업 유형 관리 |
| 안전 서약 | `pledge.html` | 일일 서약 대상 지정, 알림 및 완료 추적 |
| 분석 | `analytics.html` | 안전 신호, 점검 통계 및 작업자 추세 |
| 관리 | `manage.html` | 작업자, 작업지시, 보고서, 푸시, 설정 및 보존 |
| 불안전 사항 | `unsafe.html` | 불안전 상태 목록, 상세 및 타임라인 |
| 자재 누락 | `materials.html` | 자재 누락 목록, 상세 및 타임라인 |

`vercel.json`은 확장자가 없는 애플리케이션 경로를 해당 정적 셸로 재작성합니다. 공통 런타임은 논리적 화면을 판별하고, 직접 URL, 데스크톱 내비게이션, 모바일 하단 내비게이션 및 브라우저 이력을 인식하는 상세 화면 흐름 전반에서 일관된 이동 동작을 유지합니다.

## 아키텍처

### 프런트엔드

- 프레임워크를 사용하지 않는 다중 페이지 HTML, CSS 및 JavaScript 구조입니다.
- 공통 애플리케이션 오케스트레이터: `assets/js/app-v2.js`.
- 관리 런타임: `assets/js/admin-v2.js`. 필요할 때 동적으로 가져오며 `assets/dist/js/admin-v2.js`로 출력됩니다.
- 공통 화면 렌더링: `assets/js/screen-views.js` 및 `assets/js/dashboard-view.js`.
- 운영 화면 모듈은 보조 화면, 거버넌스, 이력, 관리, 자재, 빠른 메뉴, 선박 및 불안전 사항을 담당합니다.
- 도메인 동작은 분석, 점검, 불안전 사항/자재, 내비게이션, 알림, 보존, 안전 설정, 상태 구조, 작업자, 작업 준비 및 가져오기를 담당하는 집중형 모델, 헬퍼 및 `*-rules.js` 모듈로 분리되어 있습니다.
- 스타일 원본은 `assets/css/`에, JavaScript 원본은 `assets/js/`에 있습니다.
- `tools/build-assets.mjs`는 번들링 없이 원본 파일을 일대일로 축소해 커밋 대상 배포 산출물인 `assets/dist/`에 생성합니다.

전역 스크립트 로드 순서와 기존 공개 함수 이름은 호환성 계약입니다. 원본 파일을 편집 대상으로 삼고, 원본을 변경한 뒤에는 생성 파일인 `assets/dist/`를 다시 빌드해 검토합니다.

### 상태, 동기화 및 데이터 안전

- Supabase는 데이터베이스 저장소, 인증/세션 지원, Realtime, Storage, RPC 및 Edge Functions를 제공합니다.
- 클라이언트는 로컬 상태와 대기 중인/오프라인 작업을 유지하고, 원격 행을 직접 조정하며, Realtime을 사용할 수 없을 때 커서 기반 폴링을 사용합니다.
- 원격 동기화는 현재 세션에 관련 데이터 접근 권한이 있을 때만 시작합니다. 로그인 전 읽기는 로그인 및 점검표 설정에 필요한 공개 기준 정보로 제한합니다.
- 대기 중인 기록은 애플리케이션 업데이트 후에도 유지되어야 하며, 해당 기록을 만든 작업자에게 계속 귀속되어야 합니다.
- 편집기 초안, 파괴적인 관리 작업, 삭제 이벤트, 재시도 및 서비스 워커 컨트롤러 변경에는 명시적인 보존 및 롤백 동작이 필요합니다.

### 백엔드

- Edge Functions는 `supabase/functions/` 아래에 있으며, `admin-mutations`, `pictogram-image`, `record-retention`, `worker-push`로 구성됩니다.
- 일반적인 스키마 변경은 `supabase/migrations/`에 있습니다.
- `supabase/cutovers/`에는 별도 승인을 받은 프로덕션 강화 단계가 있으며, 일반 마이그레이션 푸시의 일부로 적용해서는 안 됩니다.
- 브라우저에 노출되는 설정은 권한 부여 경계가 아닙니다. 민감한 변경 및 알림 전송은 서버 측 함수와 데이터베이스 정책으로 검증합니다.

### 호스팅 및 PWA

- Vercel은 정적 애플리케이션을 제공하며 `vercel.json`을 통해 리디렉션, 재작성, 캐시 헤더 및 CSP를 정의합니다.
- `manifest.json`은 설치 가능한 애플리케이션을 정의합니다.
- `sw.js`는 애플리케이션 버전, 자산 토큰, 셸 캐시, 업데이트 확인 및 제어 중인 탭의 새로고침 동작을 조정합니다.
- 릴리스 및 캐시 토큰 이력은 `VERSION.md`에 기록합니다.
- GitHub 기본 브랜치, Vercel Preview 및 프로덕션 별칭은 서로 별개의 상태입니다. `main`, 통과한 Preview 또는 `READY` 배포만으로 프로덕션 상태를 추정해서는 안 됩니다.

## 저장소 구성

| 경로 | 역할 |
|---|---|
| `assets/js/` | JavaScript 원본 및 도메인/화면 모듈 |
| `assets/css/` | CSS 원본 및 반응형 디자인 토큰/컴포넌트 |
| `assets/dist/` | 생성되어 커밋되는 배포 산출물 |
| `supabase/functions/` | 인증된 서버 측 변경 및 전송 경계 |
| `supabase/migrations/` | 일반적인 데이터베이스 스키마 변경 |
| `supabase/cutovers/` | 수동 승인을 받은 프로덕션 전용 강화 단계 |
| `tests/` | Node 기반 회귀 테스트 |
| `tools/` | 자산 빌드, 품질 검사, 로컬 서버 및 브라우저 E2E 도구 |
| `docs/handoff/` | 현재 및 날짜별 운영/릴리스 상태 |

정식 GitHub 저장소는 `spahdhkd-sketch/shipyard-checklist`입니다. 활성 브랜치, 정확한 SHA, 배포 관계 및 아직 확인이 필요한 경계는 여기에 중복 기재하지 않고 `docs/handoff/CURRENT.md`에서 관리합니다.

## 검증 모델

- `npm run verify`는 저장소 구문 검사와 Node 회귀 검증을 실행합니다.
- `npm run build:assets`는 원본으로부터 커밋 대상 배포 산출물을 다시 생성합니다.
- `node tools/quality-harness.mjs --skip-verify --allow-non-main`은 기능 브랜치에서 저장소, 릴리스, HTML, 보안, 동기화, PWA 및 배포 불변 조건을 검사합니다.
- `npm run e2e`는 격리된 브라우저 흐름을 실행하고 실제 Supabase 요청을 차단합니다.
- `npm run e2e:design-tokens`는 데스크톱 및 현장 모바일 너비에서 반응형 UI 표면을 검증합니다.
- `npm run e2e:pwa`는 서비스 워커 및 업그레이드 동작을 검사합니다.
- `git diff --check`는 공백 오류와 패치 무결성을 검사합니다.

로컬 테스트 통과는 테스트한 코드 상태에 대한 증거일 뿐, 프로덕션 배포, 프로덕션 별칭, 실제 알림 수신 또는 데이터베이스 컷오버의 증거가 아닙니다. 이러한 표면에는 각각 정확한 SHA와 실제 상태에 대한 별도의 증거가 필요합니다.

## 엔지니어링 불변 조건

1. **데이터 안전 우선:** UI 오류, 재시도, Realtime 이벤트, 폴링 응답 또는 서비스 워커 새로고침으로 인해 기록이 조용히 삭제, 중복 또는 재할당되어서는 안 됩니다.
2. **인증과 권한 부여는 별개:** 클라이언트 측 제한은 동작을 개선하고, 서버 함수와 데이터베이스 정책은 권한을 강제합니다.
3. **Preview는 프로덕션이 아님:** 명시적 승인과 정확한 SHA 검증 없이 Preview가 `gs-safety-checklist.vercel.app`을 이동시켜서는 안 됩니다.
4. **원본과 배포 산출물의 일치:** 원본을 편집하면 배포 산출물을 다시 생성하고 검토해야 합니다.
5. **릴리스 토큰의 일관성:** 승인된 릴리스에서는 앱 버전, 서비스 워커, HTML 쿼리 토큰, 테스트, 품질 하네스 및 `VERSION.md`가 일치해야 합니다.
6. **모바일은 주요 사용 표면:** 영향을 받는 업무 흐름은 데스크톱 너비뿐 아니라 360~430px에서도 사용할 수 있어야 합니다.
7. **현장 UI는 한국어 및 라이트 테마 전용 유지:** 명시적인 제품 결정 없이 데스크톱 전용 상호작용이나 암묵적인 테마 전환을 도입하지 않습니다.
8. **비밀 정보와 작업자 식별 정보 보호:** 보고서와 인수인계 문서에서 자격 증명, 세션 자료, 사번 및 개인을 식별할 수 있는 작업자 데이터를 제외합니다.
9. **관리 쓰기는 명시적으로 수행:** 파괴적 작업, 실제 알림 전송, 프로덕션 데이터 변경 및 릴리스 작업에는 명시적인 승인과 눈에 보이는 성공/실패 처리가 필요합니다.
10. **복구 산출물 격리:** 과거 인수인계 문서, 패치 및 프로토타입은 증거이며, 자동으로 적용할 수 있는 원본 변경이 아닙니다.

## 기준 문서

다음 문서를 함께 사용합니다.

1. `docs/project/PROJECT_BRIEF.md`: 지속적으로 유효한 제품, 아키텍처, 저장소 및 엔지니어링 맥락.
2. `docs/handoff/CURRENT.md`: 활성 브랜치, 릴리스/배포 관계, 검증된 동작, 보존된 입력, 미해결 결함 및 다음 작업.
3. `VERSION.md`: 애플리케이션 릴리스 및 일관되게 조정된 PWA 캐시 기록.

이전의 루트 수준 문서와 날짜별 인수인계 문서는 과거 증거로 남겨 둡니다. 해당 문서가 `docs/handoff/CURRENT.md`와 충돌할 경우 현재 인수인계 문서를 기준으로 합니다.
